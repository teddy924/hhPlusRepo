# Kafka 도입 보고서

## 1. 카프카를 사용하는 목적

Kafka는 대규모 트래픽 환경에서 **분산 메시지 브로커**로서 핵심적인 역할을 수행합니다.  
단순한 비동기 통신 수단을 넘어, **서비스 간 데이터를 안정적이고 확장성 있게 교환할 수 있는 중앙 허브 역할**을 맡습니다.

특히 주문 서비스에서는 외부 데이터 플랫폼으로 주문 정보를 **중앙화된 메시지 시스템**을 통해 전송할 필요가 있었고, 이 과정에서 Kafka는 다음과 같은 방식으로 활용됩니다:

- **서비스 간 메시지를 분산 구조로 전달**
- **하나의 메시지를 여러 Consumer에게 fan-out 가능**
- **장애 발생 시 메시지를 보존하고 재처리 가능**
- **서비스 간 결합도 제거 및 유연한 아키텍처 구성**
- **높은 처리량과 확장성 보장**

Kafka는 단순한 메시지 큐가 아니라, **데이터 흐름을 제어하고 유연한 시스템 연계를 가능하게 하는 핵심 인프라**입니다.

---

## 2. Kafka의 구성요소 설명

| 구성 요소 | 설명 |
|-----------|------|
| **Producer** | 메시지를 Kafka로 발행하는 역할. 주문이 생성되었을 때 이벤트를 `topic`으로 전송 |
| **Consumer** | Kafka `topic`에서 메시지를 수신하여 처리하는 역할. 외부 데이터 플랫폼에서 소비하거나 내부 이벤트 처리 |
| **Broker** | Kafka 서버 단위. 메시지를 저장하고 전송함. 다수의 broker로 클러스터를 구성하여 분산 처리 가능 |
| **Topic** | 메시지를 분류하는 단위. 예: `order.created.v1` |
| **Partition** | Topic 내부의 데이터 샤딩 단위. 병렬 처리 및 확장성 확보에 사용됨 |
| **Consumer Group** | 다수의 consumer가 하나의 그룹으로 묶여 메시지를 나눠 소비하도록 구성. 파티션 단위로 메시지를 분산 |
| **Rebalancing** | Consumer의 수나 할당이 바뀌었을 때 파티션을 다시 배분하는 과정. 일시적으로 메시지 소비가 지연될 수 있음 |

## 3. 외부 데이터 플랫폼 주문 정보 전송 기능에 Kafka를 적용한 이유

기존의 동기 방식(API 연동 등)은 다음과 같은 문제를 가지고 있었습니다:

- **확장성 부족**: 외부 플랫폼 증가 시마다 새로운 연동 로직 필요
- **에러 복구 어려움**: 요청 실패 시 재처리 로직 필요

Kafka를 도입함으로써 다음과 같은 이점을 얻었습니다:

- 주문 도메인은 이벤트만 발행하고, 외부 전송은 consumer에서 분리 처리
- 실패한 이벤트는 재시도 가능 (Dead Letter Queue, offset 관리)
- 외부 플랫폼 추가 시 consumer만 증설하여 유연하게 확장 가능

## 4. Kafka의 장단점

### ✅ 장점

- **고성능 / 고처리량**: 초당 수십만 건의 메시지 처리 가능
- **내결함성**: replication 설정을 통한 장애 복구 가능
- **유연한 확장성**: producer/consumer 수평 확장 가능
- **메시지 영속성**: 디스크 기반 저장으로 일정 기간 메시지 보존
- **비동기 이벤트 기반 구조**: 서비스 간 결합도 최소화

### ❌ 단점

- **복잡한 운영**: 클러스터 구성 및 관리, 모니터링 부담
- **초기 학습 비용**: 개념 이해와 설정이 복잡함
- **메시지 순서 보장 제한**: partition 내에서만 순서 보장
- **Rebalancing 문제**: consumer 변화 시 일시적인 소비 중단 발생

## 5. Kafka의 단점을 보완할 수 있는 대안

| 대안 | 설명 | 보완 가능 단점 |
|------|------|----------------|
| **RabbitMQ** | 보다 간단한 메시지 브로커. 낮은 지연, 복잡도 낮음 | 운영 복잡도, 학습 곡선 |
| **Redis Streams** | Redis 기반 lightweight message queue | 초경량 큐, 빠른 처리 속도 |
| **Apache Pulsar** | Kafka 대체제로 주목. topic-level 확장성 및 message acknowledgment 우수 | 메시지 순서, Rebalancing 문제 |
| **Database Outbox Pattern** | DB 트랜잭션 로그 기반 이벤트 처리 (CDC 기반) | 트랜잭션 정합성 문제 해결 |

---

## 📌 결론

Kafka는 대규모 데이터 처리에 적합한 강력한 메시징 플랫폼입니다.  
주문 → 외부 전송과 같은 **도메인 간 데이터 연동**에서는 Kafka가 적절한 선택이지만, 운영 환경에 따라 경량 메시지 브로커나 Outbox 패턴을 병행하여 보완하는 것도 고려할 수 있습니다.
