# 📄 Kafka 기반 동시성 제어 및 이벤트 처리 구조 전환 보고서

## 1. ✅ 개요

기존 Redis 기반의 동시성 제어나 비동기 처리 방식은 단일 노드 환경에 최적화되어 있어 확장성과 처리량 측면에서 한계를 보였습니다. 본 보고서는 Kafka 기반으로 **선착순 쿠폰 발급 기능을 병렬/순차 처리 구조**로 전환하고, **Outbox Pattern**을 통해 데이터 일관성을 보장한 구조에 대해 설명합니다.

---

## 2. 🎯 전환 배경 및 목표

| 항목 | 기존 방식 | 개선 방식 |
|------|-----------|-----------|
| 동시성 제어 | Redis 분산 락 | Kafka 파티션 기반 병렬 처리 + 동시성 제어 |
| 이벤트 처리 | Redis pub/sub 또는 스케줄러 기반 | Kafka Producer/Consumer 기반 비동기 처리 |
| 확장성 | 단일 인스턴스 성능 의존 | 파티션 확장을 통한 수평적 확장 |
| 데이터 일관성 | Redis 상태 관리로 보장 어려움 | Outbox Pattern 기반 DB 트랜잭션 내 처리 |

---

## 3. ⚙ 아키텍처 설계

### Kafka 기반 Outbox 구조

```text
[사용자 요청]
     ↓
[서비스 → DB 저장 (트랜잭션 내부)]
     ↓                        ↘
[OutboxEvent 저장]         [업무 로직 실행 완료]
     ↓
[KafkaProducer 발행 (Scheduler)]
     ↓
[Kafka Topic → Consumer → 실제 로직 처리]
```

- **OutboxEvent 테이블**에 먼저 이벤트를 insert 하고,
- Kafka 발행은 트랜잭션 이후 Scheduler 혹은 Worker가 담당하여 **"트랜잭션과 메시지 전송을 분리"**합니다.
- 이를 통해 **이벤트 유실 없이 일관성 있는 처리**가 가능해졌습니다.

---

## 4. 🧪 선착순 쿠폰 발급 구조

### 1) 병렬 처리 구조

- **Kafka Topic**: `coupon.FCIssued.v1`
- **파티션 수**: 3개 (요청량 대비 확장 가능)
- **키 전략**: `couponId` → 같은 쿠폰 ID는 동일 파티션에 배정 (동시성 처리 안전)
- **동시성 제어**: 파티션 내 순차 소비 특성을 이용하여 `@Transactional` + DB Lock 기반 처리

### 2) 흐름 요약

```text
사용자 발급 요청
 → Outbox 테이블에 기록
 → Kafka 발행
 → Consumer에서 쿠폰 수량 확인 및 발급 이력 저장
```

---

## 5. 📌 Outbox Pattern 적용 이유

Kafka와 도메인 로직이 강하게 결합될 경우, 다음과 같은 문제들이 발생할 수 있습니다:

- 메시지 발행 실패 → 데이터 유실
- DB 반영 완료 후 메시지 발행 실패 → 시스템 상태 불일치
- 메시지 발행 성공했지만 DB 커밋 실패 → 중복 처리

따라서 **Outbox Pattern**을 도입하여, **트랜잭션 내에서 DB와 이벤트 데이터를 동시에 처리**하고,
이후 별도 Worker가 Kafka로 이벤트를 발행함으로써 **데이터 정합성 및 재처리 가능성**을 확보했습니다.

---

## 6. 📈 기대 효과

- **처리량 증가**: 파티션 수를 조절해 수평 확장 가능
- **중복/유실 방지**: Outbox 기반 일관성 처리
- **도메인 독립성 향상**: Kafka 메시지 중심의 비동기 구조
- **운영 대응성 향상**: DLQ 및 재처리 전략 적용 용이

---

## 7. ✅ 결론

Kafka 기반 구조 전환은 단순한 기술 교체가 아닌, **처리 성능, 일관성, 유지보수성** 모두를 향상시키기 위한 전략적인 설계 변경이었습니다. 특히 Outbox Pattern을 통한 **트랜잭션 내 메시지 기록**은 비동기 구조에서도 데이터 신뢰성을 확보하는 핵심적인 역할을 합니다.
