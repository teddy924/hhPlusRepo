## 📄 MSA 전환 및 분산 트랜잭션 처리 구조 보고서

### 1. 개요
기존 시스템은 단일 애플리케이션 내에서 유저, 상품, 주문, 결제, 쿠폰 기능을 모두 포함하고 있는 모놀리식 구조로 구성되어 있었다. 이 구조는 초기 개발 속도에는 유리하지만, 도메인 간 결합도가 높고 트래픽 증가나 도메인별 책임 분리 요구가 커질수록 유지보수가 어려워지는 문제가 있었다.

이에 따라 본 프로젝트는 기능별 마이크로서비스 아키텍처(MSA)로 전환하여 서비스 간 책임과 데이터를 분리하고, 독립 배포 및 확장을 가능하게 하는 구조로 개편하고자 한다.

---

### 2. MSA 도메인 분리 기준
도메인 분리는 다음 기준에 따라 수행되었다:

- **비즈니스 기능의 독립성:** 각 서비스가 자신의 책임을 명확히 가지고 비즈니스 로직을 독립적으로 수행할 수 있도록 분리
- **데이터 소유권:** 각 서비스는 자신이 소유한 엔티티에 대한 데이터만 관리하며, 타 도메인의 데이터를 직접 조작하지 않음
- **변경 가능성의 독립성:** 자주 함께 변경되는 기능은 하나의 서비스에 두고, 서로 다른 배포 주기/변경 주기를 가지는 기능은 분리

| 도메인     | 책임                                         |
|---------|----------------------------------------------|
| account | 회원 가입, 인증, 유저 정보 관리              |
| product | 상품 등록, 조회, 재고 관리                  |
| order   | 주문 생성, 주문 상태 변경, 주문 조회         |
| payment | 결제 요청, 결제 취소, 결제 상태 추적         |
| coupon  | 쿠폰 발급, 쿠폰 사용, 쿠폰 정책 관리         |

---

### 3. MSA 구성 구조

- **도메인 서비스 (5개):** 각각 독립된 Spring Boot 프로젝트 및 데이터베이스로 구성
- **중간 조합 서비스 (API Gateway):** 프론트엔드 요청을 받아 도메인 서비스들을 조합하여 응답 제공. 요청 단위로 흐름을 관리하며, 각 도메인의 상태를 조율하는 오케스트레이터 역할도 수행함

구조 예시:
```
[ UI ]
   |
[    API Gateway (Orchestrator)   ]
   |        |       |     |      |
 account product coupon order payment
```

### 4. 분산 트랜잭션 문제 및 대응

단일 트랜잭션 환경에서는 하나의 메서드 내에서 여러 작업이 하나의 트랜잭션으로 묶여 원자성을 보장받을 수 있었다. 하지만 MSA 구조에서는 서비스 간에 네트워크를 통한 호출이 발생하고 각 서비스는 자신만의 로컬 트랜잭션을 가지므로, 다음과 같은 문제가 발생한다:

- 일부 서비스 작업 성공 후, 다음 단계에서 실패할 경우 이미 반영된 이전 작업의 롤백이 어려움
- 네트워크 오류, 타임아웃, 장애 등으로 실패 상황이 더욱 빈번하게 발생할 수 있음

이를 해결하기 위해 보상 트랜잭션 기반의 Saga 패턴을 적용하여 일관성과 복구 가능성을 확보하였다.

---

### 5. 보상 트랜잭션 처리 흐름

본 프로젝트에서는 **Orchestration 기반 Saga 패턴**을 채택하였다. 선택한 이유는 다음과 같다:

- **프로세스 제어가 명확함:** 주문 생성과 같은 복합 트랜잭션의 흐름을 API Gateway 또는 별도의 Orchestrator가 전담함으로써, 전체 프로세스 흐름을 추적하고 제어하기 용이함
- **보상 로직의 통합 관리:** 각 단계에서 실패 발생 시, Orchestrator가 명확한 기준에 따라 보상 트랜잭션(재고 복원, 쿠폰 사용 취소 등)을 순차적으로 발행할 수 있음
- **서비스 간 결합 최소화:** 개별 도메인 서비스는 오직 자신의 도메인 이벤트에 대해서만 리스닝하며, 직접 서로를 호출하지 않음 → 느슨한 결합 구조 유지 가능
- **복잡한 로직 집중 관리:** 주문 생성 시 상품 재고 차감, 쿠폰 사용, 결제 요청 등 다양한 도메인 호출이 하나의 흐름 안에서 발생할 때, 흐름 복잡도를 Gateway에서 통제 가능

#### 📌 예시 흐름 (결제 실패 시 보상)

1. API Gateway가 다음 순서로 도메인 호출:
   - 상품 재고 차감 → 쿠폰 사용 처리 → 결제 요청
2. 결제 실패 시, Gateway가 다음 보상 이벤트 발행:
   - `rollback.coupon` → 쿠폰 사용 취소 요청
   - `rollback.stock` → 상품 재고 복원 요청
3. 쿠폰 서비스, 상품 서비스는 해당 이벤트를 Kafka 등에서 구독하여 비동기적으로 복구 수행

---

### 6. 이벤트 기반 통신 구조

- **중앙 메시지 브로커:** Kafka 사용
- **발행자:** API Gateway (Orchestrator 역할)
- **구독자:** 각각의 도메인 서비스에 구성된 Listener
- **이벤트 예시:**
  - `rollback.stock`, `rollback.coupon`, `order.created`, `payment.failed`

서비스 간 직접 호출 대신 이벤트 발행을 통해 상태 전파 및 복구를 수행함으로써, 각 서비스는 독립성과 유연성을 유지할 수 있음.

---

### 7. 구현 고려 사항

- **Idempotent 보상 로직 설계:** 동일한 보상 이벤트가 여러 번 도달하더라도 결과가 중복되지 않도록 구현
- **이벤트 트래킹:** Saga ID 기반으로 이벤트 흐름 추적 가능해야 함
- **장애 복구:** 이벤트 재처리 등 보장 메커니즘 필요
- **모니터링 및 로깅:** 각 단계의 상태를 관찰 가능한 형태로 기록

---

이 구조는 도메인 독립성, 트래픽 분산, 장애 대응력 모두를 갖춘 안정적인 분산 시스템 아키텍처로의 전환을 목표로 한다.
