## 📄 실시간 쿠폰 발급 기능 설계 보고서 (Real-Time Coupon Issuance Design Report)

### ✅ 개요
기존에는 일반 쿠폰 발급 기능을 통해 유효기간 및 중복 여부 등을 확인한 후 발급하는 방식이 사용되었으나, **한정 수량의 선착순 쿠폰 발급** 요구사항이 추가됨에 따라 별도의 실시간 쿠폰 발급 기능을 설계하고 구현하였다.

### ⚖️ 일반 발급과 실시간 발급 기능의 분리 이유
| 구분 | 이유 |
|------|------|
| 비즈니스 로직이 명확히 다름 | 선착순은 "수량 경쟁"이 핵심이고, 일반 발급은 "조건 충족 여부"가 핵심임 |
| 성능 요구가 다름 | 선착순은 Redis 기반의 고속/고동시성 처리가 중요함 |
| 검증 방식이 다름 | 일반 발급은 유효기간, 중복 여부만 확인하면 되고, 선착순은 순위/재고까지 따져야 함 |
| 스케일링 전략이 다름 | 일반 발급은 RDB 중심, 선착순은 Redis 기반으로 확장하는게 맞음 |
| 유지보수와 테스트 분리 | 하나로 섞으면 if/switch 로직이 복잡해지고 테스트가 어려워짐 |

---

### 🚀 캐시 전략
- **전략**: 발급 시도 시 Redis 캐시에 유저 ID를 삽입 및 검증 → 최종 DB 반영은 배치로 처리
- **이유**:
  - 트래픽 급증 시점에서도 빠른 응답 보장
  - 캐시 선착순 로직으로 경쟁 처리
  - 비핵심 기능(이력 저장)을 별도 처리로 안정성 확보

---

### 🧱 사용된 Redis 자료구조
| 자료구조 | 목적 |
|----------|------|
| `ZSet`   | 선착순 대기열 관리 (score = 발급 시각) |
| `Set`    | 발급 여부 중복 체크 |

---

### 🔐 재고 검증 로직
- Redis `ZSet`을 통해 유저의 발급 순서를 판별
- DB 조회로 총 발급 가능 수량, 남은 수량 모두 체크하여 **더블 체킹(Double Check)** 적용

---

### ⏱️ DB 동기화 방식
| 항목 | 전략 |
|------|------|
| 재고 차감 | 스케줄러 기반 (1분 간격), Redis -> DB 반영 |
| 발급 이력 저장 | 비동기 처리 (`@Async`)로 발급 지연 최소화 |

> 이력 저장이 실패하더라도 핵심 기능인 발급 성공에는 영향을 주지 않도록 설계하였음. 발급 이력 저장은 후속 처리를 위한 참고용일 뿐, 기능의 핵심 결과를 결정짓는 요소가 아니기 때문에 비동기 처리를 선택.

---

### ✅ 결론
실시간 쿠폰 발급 시스템은 다음과 같은 장점을 제공한다:
- 높은 동시성 환경에서도 안정적인 응답
- Redis 기반으로 RDB의 부하 최소화
- 스케일링 및 유지보수 용이성 확보
- 핵심 기능과 비핵심 기능의 분리로 탄탄한 아키텍처 구성

> 추후 이 구조는 이벤트성 쿠폰, 타임세일, 좌석 예매 등에도 유사하게 확장 가능하다.
